# 光/自旋算电协同架构 —— 高保真容错仿真报告

> 角色：HPC 架构师。目标：验证「极端恶劣机房 + 高频攻击 + 频繁 OOM」下
> \*\*系统级误判率 < 0.01%\*\* 且 \*\*端到端闭环延迟 < 10 ns\*\*。
>
> 仿真规模：`--seconds 1000 --procs 8`，即 \*\*10⁶ 次攻击注入 + 1.67×10³ 次 OOM\*\*，
> 覆盖完整 \*\*25\~85℃\*\* 温度漂移，评估 \*\*10¹⁵ 个时钟周期\*\*。
> 原始输出见 \[run\_final.log](run\_final.log)，结构化结果见 `hpc\_results.json`。

## 0\. 结论

|指标|目标|实测（需求书器件）|判定|
|-|-|-|-|
|端到端闭环延迟|< 10 ns|**5031 ps**|达标（固定硬件级联，与并行度无关）|
|系统级误判率|< 0.01%|**7.25×10⁵ ×**（相对注入次数）|**未达标**|
|假阳性抑制率|—|**124 : 1**|远低于"3 路投票 + 3 周期迟滞"应有的 10⁶\~10¹²|
|L1 假阳性率 10\~20%|需求书给定|**该器件物理上不存在**|见 §2|

（作为对照，物理自洽器件 U0/kT=80 的误判率为 6.86×10⁻¹²，远优于目标——这说明
"能否达标"完全取决于 L1 器件参数，而需求书给的参数组合自相矛盾。）

**四个必须先在工程上解决的问题（均为需求书内部矛盾，不是仿真精度问题）：**

1. **「1 ps 可靠翻转」与「10\~20% 假阳性率」不能同时成立**（§2）
2. **「3 周期迟滞」在本架构时间尺度上几乎不提供抑制** —— 连续 3 个周期是*同一次物理事件*（§3）
3. **「10 ns 闭环」与「L2 动态阈值校准」不能同时成立** —— 反馈控制无法在 10 ns 内收敛（§6）
4. **多进程 / GPU 无法缩短单事件延迟** —— 本机实测开销比预算大 4\~7 个数量级（§5）

## 2\. 物理边界核算：10\~20% 假阳性率不可实现

`physics\_check.py` 的反解关系（Arrhenius，`U\_eff/kT = U0\_over\_kt·(T\_ref/T)`）：

```
P\_false(25℃) = exp(-U0\_over\_kt)
```

|目标 FPR|需要的 U0\_over\_kt|
|-|-|
|20%|**1.609**|
|15%|1.897|
|10%|2.303|
|1e-4|9.21|
|1e-9|20.72|

* **1 ps 可靠翻转**要求 `Γ = f0·exp(-U0/kT)` 在 1 ps 内极小 → `U0/kT ≥ 20`
（此时 1 ps 内自发翻转概率 < 1e-9）
* **10\~20% 假阳性率**要求 `U0/kT ≈ 1.6` → 1 ps 内自发翻转概率 **≈ 31%**

**两者要求的器件参数方向相反，不存在同时满足的工作点。**
势垒只有 1.6 kT 的"器件"没有判决能力，它就是随机数发生器。

Arrhenius 只能把假阳性率放大**数倍**（U0/kT=1.609 时，25→85℃ 使 FPR 从 20% 升到 46%），
不可能凭空造出 10\~20%——需求书把原因和结果搞反了。

## 3\. 核心发现：3 周期迟滞在本架构时间尺度上失效

需求书要求「连续 3 个时钟周期检测到异常才输出」。但**连续 3 个周期看到的是不是同一件事**，
取决于 L1 状态寿命与 `T\_CLK` 的比值。定义：

```
rho = P(下个周期仍投票通过 | 本周期通过)
```

定性实验（20 万周期，`p = 0.063`）：

|L1 状态寿命|迟滞抑制比|说明|
|-|-|-|
|`<< T\_CLK`（rho→0，各周期独立）|**306×** ≈ `1/p²`|迟滞滤波有效|
|`>> T\_CLK`（rho→1，状态持续）|**1.0×**|**迟滞完全失效**|

**本架构落在后者**：10 ps 的 `T\_CLK` 内，3 个 L1 单元的联合状态是**一个物理事件**；
相邻周期仅隔 10 ps，而 L1 状态寿命在 ps 量级。因此「连续 3 周期都命中」
不是 3 次独立检测，而是**同一次事件被数了 3 遍**。

### 实测结果（10¹⁵ 周期，需求书器件 U0/kT=1.609）

|量|值|
|-|-|
|L1 假触发期望|9.00×10¹³ 次|
|L2 投票通过|7.26×10¹¹ 周期|
|**迟滞输出（物理工作点 rho≈1）**|**7.26×10¹¹ 次**|
|迟滞输出（乐观下界，独立极限）|6.36×10⁹ 次|
|**假阳性抑制率**|**124 : 1**（仅来自 3 路同时性，迟滞无贡献）|

两种极限下**目标都不达标**：乐观下界也已超出 `< 0.01%` 目标 4 个数量级以上。
即 `7.25×10⁵` 次误判 / 每次注入 —— **误判次数比注入次数多 5 个数量级，架构完全饱和**。

### 持续性敏感性扫描（实测）

|rho|期望误判率(/周期)|相对 rho=0|
|-|-|-|
|0.000（独立）|6.59×10⁻⁵|1.0×|
|0.500|6.39×10⁻⁴|9.7×|
|0.900|4.40×10⁻³|66.8×|
|0.990|6.90×10⁻³|104.7×|
|0.999（持续）|7.22×10⁻³|**109.6×**|

**rho 从 0 变到 1，抑制能力差 110 倍。** 这个参数需求书里完全没有，
但它才是决定"3 周期迟滞是否有效"的第一性参数。

### 为什么本轮的蒙特卡洛不能作为结论（如实说明）

MC 取"每箱一个代表采样"（已是全时间轴均匀抽样）得到 63,854 次输出，
而解析积分给出 7.26×10¹¹ 次——**两者差 7 个数量级，且 MC 偏低**。
原因：MC 每个 10 μs 箱只掷一次骰子，对同一个温度跨越 3 个箱时，
"3 连击"被算成了需要 3 次独立幸运抽中，严重低估了持续状态的连击。
**对这类极小概率 + 强时间相关过程，解析积分是正确工具，MC 只能给出量级参照。**
报告中所有结论均以解析积分与解析上下界为准。

## 4\. 端到端延迟：5031 ps 达标，但结论比看上去脆弱

关键路径（严格串行，多进程/GPU 都无法缩短）：

|阶段|累计|说明|
|-|-|-|
|环境采样 → L1 输入建立|0 ps|组合逻辑|
|L1 自旋物理翻转|**1 ps**|需求书给定|
|L2 3 路投票 + 3 周期迟滞确认|**31 ps**|迟滞跨 3 个 `T\_CLK = 10 ps`|
|执行层 PMU 反射|**5031 ps**|需求书给定 5 ns，**占总延迟 99.4%**|
|**合计**|**5031 ps**|预算 10000 ps，裕度 4969 ps|

瀑布图见 [latency\_waterfall.svg](latency_waterfall.svg)。

**三点必须澄清：**

**① L2 的 500 ps 处理延迟不在关键路径上。** 需求书同时把 500 ps 定义为
「处理延迟」和「3 路同时性的投票窗口」。投票在此窗口内完成，与检测并行推进。
若按字面串联（1 + 500 + 30 + 5000 = 5531 ps）仍 < 10 ns，结论不变；
但**若迟滞的 3 个周期也按 500 ps 计**，则 1 + 500 + 1500 + 5000 = **7001 ps**，
裕度只剩 3 ns。

**② 「500 ps 投票窗口」与「3 个时钟周期」是两个时间粒度，需求书把它们混为一谈。**
早期实现把二者都取 500 ps，导致**迟滞永远无法满足**（单周期内不可能有 3 个时钟沿）。
本实现显式分离：`VOTE\_WINDOW\_PS = 500`、`T\_CLK\_PS = 10`。

**③ 执行层的 5 ns 只够"发出"动作，不够"完成"动作。**
「GPU 降频」需要 PLL 重锁（μs 级），「KV Cache 下沉」需要 DRAM/NVMe 写入（100 ns \~ 100 μs 级）。
需求书混淆了「发出命令」与「完成动作」——必须明确延迟预算统计到哪一步，
否则 5031 ps 这个"达标"只是名义上的。

## 5\. 为什么多进程/GPU 帮不上延迟（本机实测）

**这是本次需求中最根本的方法论错误：并行化提升吞吐，不降低单事件延迟。**

|实测项|数值|与 10 ns 预算之比|
|-|-|-|
|单事件端到端（固定硬件级联）|5031 ps|0.50×|
|进程 spawn 开销|420 ms/进程|**4.2×10⁷ ×**|
|结果回传（文件式；IPC 被沙箱禁用）|423,164,525 ns|**4.2×10⁷ ×**|
|CUDA 上下文初始化（参考量级）|100\~500 ms|\~10⁷ ×|
|CUDA kernel 启动（参考量级）|3\~10 μs|\~10³ ×|
|L1 概率核单次调用（numpy）|16,800 ns|**1.68×10⁶ ×**|
|L1 概率核摊薄吞吐（numpy）|62.6 ns/元素|6.3×|
|L2 仲裁核摊薄（numpy / torch CPU）|17.2 / **7.6** ns/周期|1.7× / 0.76×|
|本仿真并行墙钟|10¹⁴ 周期 / 8 进程 / 83.4 s|—|

**两条硬结论：**

1. **任何跨越主机进程边界、PCIe 总线或 CUDA kernel 启动的操作，
开销都比整个 10 ns 预算大 3\~7 个数量级。** 10 ns 闭环只能由专用硬件状态机实现。
2. **GPU 卸载对单事件延迟是负收益。** GPU 只配用于**离线统计**——
L2 仲裁核（3 路投票 + 迟滞）的批量计算正是 GPU 的理想负载，
实测 torch CPU 版已达 7.6 ns/周期摊薄，上 GPU 还能再快数倍。
但把 GPU 放进控制回路 = 引入微秒级抖动，直接违反 10 ns 预算。

**并行化真正的价值**在本仿真中被正确使用了：10¹⁴ 个周期的统计评估
切分到 8 个进程，83 秒完成。这是吞吐问题，与延迟无关。

## 7\. 工程可扩展性修复记录（真实踩到的坑）

|问题|现象|修复|
|-|-|-|
|环境层 OOM|1 ms 网格 × 全量 = 1.25×10⁹ 点/块，**9.31 GB**|worker 内按环境网格切子块，峰值内存与总时长解耦|
|采样网格过粗|1 ms 箱抹平箱内温度涨落（FPR 对温度是指数的），模式 B 算出 **>100%** 误判率|环境采样网格收到 **10 μs**|
|连击计数错误|把「3 连击」当成每个环境步一次，实际是 `cycles\_per\_env` 次|乘上 `runs\_per\_sample`|
|迟滞语义错误|把 500 ps 投票窗口当成迟滞时钟，迟滞**永远无法满足**|分离 `VOTE\_WINDOW\_PS`(500) 与 `T\_CLK\_PS`(10)|
|迟滞物理语义错误|按"各周期独立"算，高估抑制能力数个量级|引入 rho 持续性模型，取物理工作点|
|rho 符号反了|`CORR\_PERSIST=0` 与"持续极限"混淆|rho 统一定义为持续性概率，默认 1.0|
|指标饱和|`p\_cycle`（阵列任一单元触发）在需求书器件下饱和到 **0.99987**，解析估计退化为 log10(1)≈0|改用 `p\_vote`（3 路同周期同时）|
|MC 抽样偏差|只取前 10⁵ 点（单一温度窗），与解析值差数百倍；stride 抽样破坏连击结构|改为每箱代表采样，并如实标注 MC 的适用边界|
|IPC 不可用|`Queue`/`Pipe`/`Pool` 全部 `PermissionError \[WinError 5]`|`Process` + 工作区 JSON 文件收集结果|
|子进程 pickle|spawn 无法序列化局部函数|工作函数全部提升到模块级|
|孤儿进程|中途改源码导致旧 worker 变孤儿占满 8 核|显式清理进程后重跑|

## 8\. 若要把这个架构做成真的，建议顺序

1. **先测 rho（L1 状态寿命 / T\_CLK）**。它决定 3 周期迟滞是否有效，
比 U0/kT 更关键。本仿真判断处于"状态持续"区间（rho≈1），迟滞需重新设计——
例如让判决时钟与器件寿命解耦，或改用跨时间的独立采样，而不是依赖连续周期。
2. **重新选 L1 工作点**：在「1 ps 翻转」与「假阳性率」之间二选一。
保留可靠翻转（U0/kT ≥ 20），把假阳性抑制完全交给 L2；
需求书的 10\~20% 假阳性率不应作为设计目标。
3. **把校准移出关键路径**：L2 阈值校准做成慢速内环（μs\~ms），关键路径只保留固定延迟。
4. **明确延迟预算统计边界**：执行层 5 ns 应定义为「命令发出」；
若要求「动作完成」，预算需按 μs\~ms 级重估。
5. **仿真与硬件分工**：CPU/GPU 只用于离线统计与参数寻优；
控制回路用 RTL/FPGA 验证，时钟按 ps 级约束。
